# T01 / T02 验收答题

1. **受控模式删除连着边的 n2，谁先收到什么？过滤能挡什么？**

   正常删除流程中，`onEdgesChange` 先收到相连边的 `{id:'n1-n2', type:'remove'}`，`onNodesChange` 再收到 `{id:'n2', type:'remove'}`。选中阶段的 select 是此前的变化。完整通知顺序是 `onEdgesDelete → onEdgesChange → onNodesDelete → onNodesChange → onDelete`（中间由 trigger*Changes 派发）。changes 层过滤能阻止对应 remove 写入受控状态，不能阻止这些回调已经发生或随后继续发生，也不能让删除回调自动知道过滤结果。需要在删除流程前否决时，应使用 `onBeforeDelete`；不能把 changes 过滤视为整个删除事务的取消。

2. **n1 设置 deletable:false，单独选中 n1–n2 按 Delete，边会删吗？**

   默认可删：节点的 `deletable:false` 只保护节点，单独删边看边自己的 deletable。若边也为 false，或者应用过滤边的 remove，才会留下。当前 B 组另外过滤了所有关联 n1 的边，因此该 demo 中边会保留；这是应用逻辑，不是节点配置自动传递给边。

3. **isValidConnection 次数不固定，哪两件事确定？**

   业务回调只在库内端口检查通过后才执行；正常拖线松手时使用最后一次移动留下的候选和校验结果，不再补调一次 `isValidConnection`。所以次数随候选命中、移动事件而变，不应该断言固定次数。

4. **从 End 输入点反向拖到 source Handle，各字段是什么？**

   假设落到 B 的 `out-alt`，`onConnect` 为 `source:'b', sourceHandle:'out-alt', target:'end', targetHandle:'in'`；`onConnectEnd.fromHandle` 则是按下时的 End 输入 Handle。source/target 根据端口类型表达有向边语义，from/to 表达拖动手势起点和落点，两者不必一致。

5. **R5 为什么不能交给 addEdge？是／否汇入同一下游时呢？**

   `addEdge` 比较两端节点及两端 Handle，换出口不算相同连接；练习 R5 则只比较有向节点对，所以更严格。若条件分支“是／否”允许汇入同一下游，R5 就不能继续忽略出口，应按节点、分支出口及目标端口识别连接，保留不同分支，只拒绝真正重复的那条边；前后端规则必须同步。分支 id 必须稳定且唯一，不能靠 null 或展示文案区分。
