## 核心机制（源码事实）

1. 【源码事实】**三套坐标与正逆换算公式**：
   - **屏幕坐标（client 坐标）**：鼠标事件 `event.clientX` / `event.clientY`，相对浏览器视口左上角。
   - **画布容器内坐标（renderer point）**：减去 `.react-flow` 根容器 `domNode.getBoundingClientRect()` 的 `{ x: domX, y: domY }` 后的相对坐标：`corrected = { x: clientX - domX, y: clientY - domY }`（`useViewportHelper.ts:91-95`）。
   - **流程坐标（flow position）**：节点 `node.position` 所在的画布内部坐标系，由 `pointToRendererPoint`（`system/src/utils/general.ts:168-180`）根据 `transform = [tx, ty, tScale]`（即 `[viewport.x, viewport.y, viewport.zoom]`）换算：
     $$x_{\text{flow}} = \frac{x_{\text{client}} - \text{domX} - tx}{tScale}, \quad y_{\text{flow}} = \frac{y_{\text{client}} - \text{domY} - ty}{tScale}$$
     若开启了 `snapToGrid`，在除以 `tScale` 得到流程坐标之后再调用 `snapPosition(position, snapGrid)` 吸附网格。
   - **反向换算 `flowToScreenPosition`**（`useViewportHelper.ts:104-119`）：先调 `rendererPointToPoint`（`general.ts:182-187`）算 `x * tScale + tx`，再加上 `domX` / `domY`：
     $$x_{\text{client}} = x_{\text{flow}} \times tScale + tx + \text{domX}$$
     在不开启 `snapToGrid` 时，`screenToFlowPosition` 与 `flowToScreenPosition` 严格互为逆运算（仅有浮点数精度误差）。

2. 【源码事实】**为什么平移和缩放画布不会触发 `onNodesChange`，也不会重渲染节点组件**：
   - `Viewport` 容器组件（`container/Viewport/index.tsx:14-56`）只用 `useStoreApi()` 订阅 `store.subscribe(applyTransform)`，在 `transform` 变化时**直接操作 DOM**：`viewportRef.current.style.transform = translate(${tx}px, ${ty}px) scale(${tScale})`。
   - 整个平移、缩放过程中，既不修改 `node.position`，也不触发 `Viewport` 的 React state 更新，更不会派发 `onNodesChange`。只有订阅了 `useViewport()` 的组件才会随 `transform` 重渲染。

3. 【源码事实】**`setViewport` 与 `fitView` 的工作链路**：
   - `setViewport`（`useViewportHelper.ts:40-59`）**不直接写 `store.transform`**，而是调用 `panZoom.setViewport({ x, y, zoom }, options)`，由 `XYPanZoom`（基于 `d3-zoom`）驱动变换（支持 `duration` 过渡动画），再由 `d3-zoom` 的 zoom 事件把新的 `transform` 写回 store。
   - `fitView(options)`（`useReactFlow.ts:296-306`）先把 `fitViewQueued: true` 和 `fitViewOptions: options` 写入 store 并触发一次队列刷新；随后在 `fitViewport`（`system/src/utils/graph.ts:375-404`）中调用 `getFitViewNodes(nodes, options)` 过滤出 `options.nodes` 指定的节点子集，用 `getInternalNodesBounds` 算出包围盒，再用 `getViewportForBounds` 算出目标 `{ x, y, zoom }` 并交给 `panZoom.setViewport`。

4. 【源码事实】**`onMoveEnd` 的 `event` 来源与 `panOnScroll` 的 150ms 延迟**：
   - `createPanZoomEndHandler`（`system/src/xypanzoom/eventhandler.ts:210-252`）把 d3-zoom 事件里的 `event.sourceEvent` 作为第一个参数传给 `onPanZoomEnd`（即 React 层的 `onMoveEnd`）。用户鼠标拖拽或滚轮操作时 `sourceEvent` 是原生 `MouseEvent` / `WheelEvent`；而程序调用 `setViewport` / `fitView` 时（特に无动画立即跳转或 d3 编程式 transition 结束时）没有原生交互事件，`event.sourceEvent` 为 `null` / `undefined`，因此 `Boolean(event)` 为 `false`。
   - 当开启 `panOnScroll` 时，滚轮滚动会連続触发多次 d3 `end` 事件，源码用 `setTimeout(..., panOnScroll ? 150 : 0)` 合并防抖，只在滚动停下 150ms 后触发一次 `onMoveEnd`。

## 预测（写在实现 V1–V4 之前）

1. **数值换算预测**：设画布容器左上角距离浏览器窗口为 `(domX, domY)`，当视口为 `{ x: 80, y: 60, zoom: 2 }` 时，若点击容器内距左边缘 `280px` 的位置（即 `clientX - domX = 280`），代入公式 $x_{\text{flow}} = (280 - 80) / 2 = 100$，预计 `flowPosition.x` 应为 `100`；再经 `flowToScreenPosition` 反算回来的 `roundTrip.x` 应等于 `clientX`。
2. **平移与缩放预测**：拖动画布空白处或滚轮缩放时，顶部 `viewport` 读数实时变化，但控制台**不会**出现 `[视口 / onNodesChange]` 日志。
3. **点击放置节点预测（V3）**：勾选“点击空白处放置节点”后，新节点使用 `screenToFlowPosition` 算出的流程坐标保存；放好后平移或缩放画布，新节点会和原有的 A、B、C 节点保持相对位置一致，一起移动和缩放。
4. **聚焦 B 与重置视口预测（V4）**：点击“聚焦 B”只把节点 B 移到画布中央并放大；点击“回到初始视口”恢复 `x = 80, y = 60, zoom = 1.00`，且程序调用触发的 `onMoveEnd` 日志中 `hasEvent` 为 `false`。

## 个人理解

1. **屏幕坐标、流程坐标与视口三者的关系**：
   - 节点的 `position` 永远是**流程坐标**（画布世界内部的不变坐标），不会因为你平移或缩放了画布而改变。
   - **视口 `viewport = { x, y, zoom }`** 是套在 `.react-flow__viewport` 容器上的摄像机变换（CSS `translate(x, y) scale(zoom)`）。
   - **屏幕坐标（client）** 是鼠标在浏览器窗口里的像素位置。只要涉及到“把鼠标点击/拖放的位置变成画布上的节点位置”，就必须先调 `screenToFlowPosition({ x: event.clientX, y: event.clientY })` 把屏幕坐标换算成流程坐标，绝不能直接把 `clientX / clientY` 当成节点的 `position`。
2. **`fitView` 与 `setViewport` 的区别**：
   - `setViewport({ x, y, zoom })` 是明确指定摄像机要去哪个坐标和缩放倍率（比如精确恢复初始视口 `{ x: 80, y: 60, zoom: 1 }`）。
   - `fitView({ nodes, padding, duration })` 是让库根据全部（或指定子集）节点的当前位置和宽高自动计算出一个能装下它们的 `{ x, y, zoom }`。所以控制栏自带的“适应视图”按钮（调 `fitView`）算出来的视口通常不等于我们的 `initialViewport`。

## 问题记录

1. **为什么调用 `screenToFlowPosition` 时要传 `event.clientX / clientY`，而不是 `nativeEvent.offsetX / offsetY`？**
   - 【源码事实】看 `useViewportHelper.ts:91-95`：`screenToFlowPosition` 内部第一件事就是调用 `domNode.getBoundingClientRect()` 并用传入的坐标减去容器左上角 `(domX, domY)`。这意味着它明确要求传入**相对浏览器视口（viewport）的 `clientX / clientY`**。如果传了 `offsetX`（相对触发事件的内部子元素）或 `pageX`（含页面滚动偏移），减完 `domX / domY` 后坐标就会错位。
