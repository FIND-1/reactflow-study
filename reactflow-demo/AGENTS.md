# React Flow 学习 Demo 项目规范

## 项目定位

- 本项目用于学习 React Flow。实现和注释应让具备 React 基础、初次接触 React Flow 的读者容易理解。
- 默认使用中文沟通和编写说明性注释，保留 API、类型和变量的英文原名，方便对照官方文档。
- 使用 pnpm 管理依赖和执行脚本，保持现有 React + TypeScript 结构。

## 按官方章节学习（必须遵守）

- 以 https://reactflow.dev/learn 的 Learn 侧栏顺序为主线：Quick Start → Core Concepts → Customization → Layouting → Advanced Use → Tutorials → Troubleshooting。各分组内遵循官网当前顺序。
- 每章保留独立示例，放在 `src/lessons/<序号>-<章节名>/`，通过 `src/lessons/index.ts` 登记并在页面中切换。不要把所有章节功能累加到同一个 Demo，也不要覆盖早期练习。
- 每次围绕当前章节阅读和练习，后续章节随学习推进再添加，不自动一次性实现全部教程。
- 每章必须提供官方链接、学习目标、对应代码文件、动手任务、预期现象及功能边界；示例已准备不等于用户已学完。
- 当前章节只引入该章需要的概念。已有 Quick Start 综合示例可保留，但要明确额外功能；Building a Flow 保持静态数据，交互状态更新在 Adding Interactivity 中练习。
- 每章组件独立管理画布状态，切换章节重新加载示例；画布操作不持久化，代码修改仍保留在源码文件中。改变这一行为时同步更新说明。
- 优先复用页面导航和通用样式；为了方便逐章对照，允许各章保留简单的节点、连线定义，不强行抽象教学代码。
- 源码阅读作为理解当前功能的补充，先读文档并动手验证，再按具体问题追踪实现；分析库内部实现时对照已安装版本。
- 维护 `docs/learning-path.md` 和 README 中的章节入口与练习说明。

## 需求与功能注释（必须遵守）

- 新增或修改功能时，在对应实现附近写清楚功能目的、触发方式和预期结果；涉及状态更新时，说明用户操作如何影响数据和界面。
- 对 React Flow 的关键概念和必要配置，用通俗中文解释用途及原因，例如节点与连线的关系、受控状态、连接点、事件回调、样式导入和容器尺寸。
- 解释 API 时结合当前示例，不只翻译名称或复述代码；首次出现的专业术语应配一句简单说明。
- 明确示例的能力边界，区分“展示流程图”和“执行真实业务”，说明刷新、重置、持久化等实际行为，不暗示尚未实现的能力。
- 注释放在对应的数据定义、函数或 JSX 功能块附近，以功能块为单位组织；简单语法和显而易见的样式不必逐行注释。
- 注释保持简短、准确、可读，优先解释“为什么这样做”和“操作后会发生什么”。不要为了增加注释数量写空泛描述。
- 修改实现时同步更新相关注释；操作方式或功能范围变化时，同步更新 README，避免说明与代码不一致。
- 描述库的行为（调用时机、执行顺序、返回值、类名等）前，先对照已安装版本的源码或官方文档核实，不凭印象写；引用源码时写明文件或函数名。
- 区分“函数/handler 是什么”与“调用后会发生什么”，例如 `useNodesState` 的第三个返回值是 handler，调用它才会更新状态，不要写成“已经应用”。
- 解释一段防御或补救逻辑时，写清它实际兜住的具体场景及去掉后的后果，不笼统写“避免出错”；若真正原因来自本示例的其他规则，要点明是哪条规则。
- 规则有副作用或覆盖范围大于字面意思时（如锁定节点连带锁住相关的边、请求被静默拒绝），在注释中写明，并同步到注册表的 `boundary` 和页面说明。
- 描述去重、过滤、计数等逻辑时，按代码实际条件表述（如“只和上一次比较”而非“只打印一次”），并说明哪些情况不会被覆盖。
- 页面颜色、状态等反馈说明要列全触发条件（如拒绝可能来自业务规则，也可能来自库内结构校验），不要只写最常见的一种。
- 注释用中性、准确的书面表达，避免“已接好”“图省事”等不提供信息的口语。

示例：

```ts
// 用户把源节点的输出连接点拖到目标节点的输入连接点后，
// 将这次连接加入 edges 状态，让新连线显示在画布上。
const onConnect = useCallback<OnConnect>((connection) => {
  setEdges((currentEdges) => addEdge(connection, currentEdges))
}, [])
```

## 修改与验证

- 修改前先阅读已有实现和相关需求，优先复用现有组件、hooks、工具和类型。
- 保持修改范围与需求一致，不为教学注释重构稳定逻辑或新增无需求依据的功能。
- 修改代码后运行 `pnpm lint` 和 `pnpm build`（包含 TypeScript 检查）；仅修改 Markdown 时检查文档准确性即可。
- 交付时说明修改文件、功能变化和验证结果，区分实际执行的检查与尚未验证的内容。

## 知识点目录约定（2026-11-05 起）

以下约定优先于上文“新增练习放入 lessons”的目录规则，官方章节仍作为阅读主线。

- `src/lessons/01-*`～`03-*` 保留为基础示例；今后新增知识点必须放进 `src/topics/NN-name/`，不要继续往 lessons 累加。
- 单章专属的画布组件（`.tsx`）、辅助规则或纯函数（`.ts`）、专属样式（`.css`）和 `README.md` 就近放在所属 `src/topics/NN-name/` 目录内，不拆到外层全局目录。跨章节共用的页面外壳、导航与工具栏通用样式（如 `.app`、`.flow-container`、`.header-actions` 及 `button[aria-pressed='true']`）统一放在 `src/App.css`；各章节 `.css` 中的选择器必须以该章根类名（如 `.connection-exercise`、`.custom-nodes-exercise`、`.viewport-exercise`）作为作用域前缀，避免污染其他章节。
- 每个知识点目录必须有 README.md，写明对应编号笔记、SOURCE_MAP 条目、练习内容、状态与功能边界。
- 在 `src/topics/index.ts` 注册 id、显示编号、知识点标题、组件、笔记路径、状态及学习指引；笔记路径相对于 demo 根目录。显示编号使用 T01、T02……，与 topics 和 notes 编号一致，标题只写知识点名。
- 新增知识点必须填写 `officialDocs: { title, url }[]` 与 `prerequisites`。`officialDocs` 可为空数组，页面不显示空文档行或占位文字；不要编造官方页面名或修改给定 URL。`prerequisites` 以 lessons 或 topics 注册表的唯一 id 数组记录，无前置时使用空数组；涉及入门关联时同步维护 `lessons/index.ts` 的 `deepensTopics`。
- 新增知识点（包括“未开始”的计划）必须同时在 `docs/learning-path.md` 的“覆盖检查表”登记；已有官方页面更新对应知识点，空文档列表则在“无官方文档的知识点登记”中列出编号和标题，后续补充链接时同步更新。官方页面的安排只使用“对应知识点 / 需要时再学 / 暂不学”；覆盖登记不代表学习已完成。
- 状态只使用“未开始 / 骨架已准备 / 实现中 / 笔记完成 / 已验收”；收尾项未完成不得标记“已验收”。未开始的计划条目只在侧栏灰色显示，不可点击，不加入 hash 页面和翻页列表。侧栏只显示“编号 · 标题”和知识点状态徽章，不显示官方文档说明；入门 A1、A2、A3 不显示状态徽章。显示编号不得改变现有目录、文件或 hash。
- 创建对应 `../notes/NN-知识点.md`，并更新工作区根 `../README.md` 的进度表；编号在 topics 与 notes 中保持一致。
- 左侧知识点导航由 topics 注册表生成，以 `location.hash` 切换，不引入路由库；基础示例继续由 lessons 注册表提供。
- 移动文件时同步更新导入、Markdown 相对链接和路径说明，并逐个检查链接与锚点；不得删除已有练习或填写学习者保留的 TODO。
- 修改导航后运行 `pnpm lint` 和 `pnpm build`，在浏览器实际打开各知识点并验证刷新、前进和后退。禁止改动工作区根的 `xyflow/`。
